# RegStack — Independent Technical Debt & Security Risk Report

**Scope:** `regstack/regstackcompliance`, branch `master` @ `77629da97fdcfbeb25020322a6aa85f878cb4310` (2026-09-19)
**Reviewer:** independent read-only inspection (a fresh subagent with no prior context on this codebase), no prior relationship to this codebase
**Method:** full read of `src/middleware/*`, `src/routes/index.ts`, `src/app.ts`, every `*.routes.ts` under `src/modules/` (44 files), `prisma/schema.prisma`, the two RLS migrations, `.env.example`, `docker-compose.yml`, `.github/workflows/*.yml`, `src/modules/contracts/objectStorage.ts`, `src/modules/backup/backupDatabase.ts`, and the relevant frontend server/client glue (`frontend/lib/regstack/*`). Findings below are grounded in the actual code read, not inferred from file names.

**Update (2026-09-20):** every Critical, the High, and both Mediums were verified against the working tree (and, where relevant, against the live production Supabase project — read-only) and fixed the same night. Resolution notes are inline under each finding. Nothing below was silently dropped or downgraded.

## Executive summary

The core security invariants the team set out to build — server-derived `institutionId` on every query, a central RBAC matrix checked on every mutating route, and a transactional audit-log write on every entity mutation — are implemented correctly and consistently across essentially the entire route surface sampled (44 route files, ~90+ mutating endpoints). Zero routes were found that trust a client-supplied `institutionId`/`userId` for authorization, and the Postgres RLS lockdown migrations correctly cover all 82 mapped tables with none missed. That said, the review surfaced a real, exploitable cross-tenant file-access gap in the contract upload flow, a structural (not just theoretical) tenant-isolation hole in the newer Supabase Storage-based file uploads, a production backup pipeline that handed out plaintext 2FA secrets and password hashes to anyone with repo Actions access, and a rate limiter that was architecturally incompatible with the app's own serverless deployment target.

## What's actually solid (unchanged by tonight's fixes)

- **RBAC coverage is thorough and correct** across all 44 route files sampled — no route reachable without the right check.
- **`institutionId` is never trusted from the client** — every scoped query derives the tenant from the verified JWT.
- **`withAudit`'s transactional design is genuinely sound** — the entity write and the audit-log insert happen in the same DB transaction.
- **The RLS migrations are complete** — all 82 original tables covered, cross-referenced against `prisma/schema.prisma`. (The new `rate_limit_buckets` table added tonight is RLS-enabled in the same migration that creates it, so this stays true at 83.)
- **Zod validation is consistently applied** everywhere a route reads `req.body`.
- **The login/2FA/session-exchange design is well thought out**, not just "it happens to work."
- **No hardcoded secrets or credentials anywhere in the repo.**
- **Indexing is thorough** — 79 `@@index` directives, matching the query patterns that need them.
- **The backup/DR documentation is honest** about its own known gaps (see `docs/backup-disaster-recovery.md` §7).

## Open item requiring a real decision

The ICS Supabase Storage tenant-isolation gap (second Critical above) is the one finding still open. It is not currently exploitable (the bucket doesn't exist in production yet), which is the only reason it wasn't fixed alongside everything else tonight rather than rushed. Recommended fix: replace the direct browser→Supabase-Storage upload in `frontend/lib/regstack/storage.ts` with a backend-brokered flow — the Express API mints a scoped upload target (embedding `institutionId` server-side, exactly like `contracts.routes.ts` / `objectStorage.ts` already do for S3), the same pattern this codebase has already proven correct. Do this before the `ics-files` bucket is ever created in production.
