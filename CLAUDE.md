# RegStack (Lumera)

Auslagerungsmanagement/Compliance backend for German leasing companies (financial institutions
regulated under KWG/MaRisk, with DORA in scope). Sold to leasing-company compliance/GL teams —
its whole value proposition is "every write is provably auditable, permissions are enforced
server-side, and the product itself would survive an audit." Treat that as the actual bar for any
change here, not just "does it work."

## Stack

- **Backend:** Node.js 20+, Express, TypeScript (strict), `src/`
- **Frontend:** Next.js, `frontend/` (has its own README/AGENTS.md — that AGENTS.md is
  auto-generated by `next dev`, not a real convention doc; ignore it)
- **DB:** PostgreSQL 16 via Prisma (`prisma/schema.prisma`), hosted on Supabase (eu-central-1)
- **Auth:** JWT (`src/middleware/auth.ts`) + optional TOTP 2FA
- **Tests:** Vitest, `tests/` — no DB dependency, run with `npm test`

## Non-negotiables (read this before touching auth/DB/routes)

These three are load-bearing for the product's entire pitch — never work around them:

1. **Audit trail on every write** — `withAudit()` in `src/middleware/auditTrail.ts` writes the
   business write and the `AuditLogEvent` row in the *same transaction*. A route that mutates data
   outside `withAudit` is a bug, not a shortcut.
2. **Server-side RBAC** — `requirePermission()` in `src/middleware/rbac.ts` re-checks role × resource
   × action on every request, independent of what the frontend shows/hides. Never trust the client.
3. **Tenant isolation** — every model hangs off `institutionId`. Always derive `institutionId` from
   the authenticated session, never from a client-supplied body/query param — that's the single
   worst bug class here (cross-company data leakage in a regulated multi-tenant product).

RLS is also enabled on every table (backend-only, no policies — see the
`20260919*_enable_rls_*` migrations) as defense-in-depth, not a replacement for #2/#3.

## Module map (`src/modules/`)

Each folder = one entity/process, mapped to a specific regulatory basis:

| Module | Regulatory basis |
|---|---|
| `outsourcingActivities`, `contracts`, `handlungsoptionen`, `monitoring`, `weiterverlagerung` | MaRisk AT 9 (outsourcing) |
| `compliance` | MaRisk AT 4.4.2 |
| `revisions` | MaRisk AT 4.4.3 (Interne Revision) — includes `externePruefungen` (external audit findings) |
| `risikomanagement`, `itRisiko` | MaRisk AT 4 / BAIT |
| `ictRegister` | DORA Art. 28-30 (ICT third-party register) — **not yet verified 1:1 against the
  official EBA/ESA ITS templates (Reg. (EU) 2024/2956)**, see `docs/dora-roi-field-gap-analysis.md` |
| `accounting`, `ics` | Bilanz/GuV/Anhang/Lagebericht + internal controls |
| `institutions`, `users`, `auditLog`, `notifications`, `backup`, `nachweise`, `reports` | cross-cutting |

Domain enums/fields frequently mirror exact German regulatory terms (`Tz.` = Textziffer/paragraph
references in comments) — don't rename these to English, they're intentionally literal.

## Conventions worth knowing before you're surprised by them

- `xxxUserId` fields (e.g. `verantwortlichUserId`) are usually **plain unrelated columns**, not
  Prisma relations — resolved to a display name via `GET /users` client-side. This is deliberate,
  not an oversight (see comments in `schema.prisma`).
- Finalized records (Bilanz, GuV, Nachweis versions, ...) are never overwritten — a correction is a
  new row linked via `previousVersionId`. Preserve this pattern for anything append-only/auditable.
- Some tables are insert-only by design (e.g. `revision_gl_mitteilungen`, `revision_sonderauftraege`)
  — don't add update/delete routes to these without checking why they're insert-only first.

## Local dev

```bash
cp .env.example .env          # fill in local DB creds
npm install
npx prisma migrate deploy
npm run seed                  # Beispiel Leasing AG + 3 outsourcing activities + demo data across all modules
npm run dev                   # http://localhost:4000, health check: /health
```

Seed users (password `regstack-dev-2026`): `geschaeftsleitung@beispiel-leasing.de`,
`compliance@beispiel-leasing.de`, `admin@regstack.de`.

Before shipping any DB/auth/route change: `npm run typecheck && npm run lint && npm test`.

## Deployment

Vercel (both `frontend/` and this backend, as separate projects) auto-deploys `master` and creates
PR previews — no separate CD step needed. `.github/workflows/ci.yml` covers lint/typecheck/test/build
only. DB is Supabase Postgres, eu-central-1. See README.md "Deployment" for the full picture and
`docs/backup-disaster-recovery.md` for the backup/restore process (independent daily `pg_dump` +
automated structural restore check in CI; full application-level restore drills are run manually —
see that doc's §3/§7 for the latest one).
